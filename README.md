From time to time Konveyor needs a newer version of Go to build projects than is available from go-toolset or other images on Quay and registry.access.redhat.com; docker.io images are usually current but rate-limit when pulled into Quay builds. The shared, variant-parametrized Dockerfiles in this repository close that gap and are published automatically by the GitHub Actions workflows linked above. The variant list lives in [`variants.txt`](variants.txt).

## Using the images

<!-- readme-usage:start generated by .github/workflows/readme-tracks.yml -->
```dockerfile
# pin an exact Go version
FROM quay.io/konveyor/builder:ubi9-v1.27.4
```

```sh
podman pull quay.io/konveyor/builder:ubi9-latest
```
<!-- readme-usage:end -->

- **Pinning**: `vX.Y.Z` pins an exact Go version, `vX.Y` tracks the newest patch of a minor as last built (a manually dispatched build of an older patch moves it back), and `latest` tracks the newest build of the variant. Note a pinned version is not a pinned image: existing versions are rebuilt when their UBI base image drifts, moving the tag to the rebuilt content — pin a manifest-list digest (`quay.io/konveyor/builder@sha256:…`) when builds must be bit-for-bit reproducible. Standard flavors publish only plain tags.
- **FIPS**: use a FIPS variant below. On the 1.27+ `hostfips` toolchains, set [`GODEBUG=fips140=on`](https://github.com/golang-fips/go#godebugfips140) to force FIPS mode regardless of the host (they default to host-auto); the ≤1.26 `openssl-fips` toolchains instead activate FIPS through the OpenSSL FIPS module and ignore that variable — to force FIPS mode on those, set `GOLANG_FIPS=1` (and, on OpenSSL 3, `OPENSSL_FORCE_FIPS_MODE=1` too) ([runtime usage](https://github.com/golang-fips/go/blob/go1.26-fips-release/README.md#forcing-fips-mode-at-runtime)). Pre-release-sourced FIPS builds publish only `-pre` tags, so a tag never overstates the release it was built from.

All images are multi-arch (`linux/amd64`, `linux/arm64`, `linux/ppc64le`, `linux/s390x`) and published to `quay.io/konveyor/builder`. SBOMs for the shipped set — the newest patch of each of the two newest Go minors per variant — are submitted to GitHub's dependency graph by [`submit-sboms.yml`](.github/workflows/submit-sboms.yml), so Dependabot alerts cover those images (alerts surface in this repository's Dependabot, where enabled). Older published versions fall outside that scan scope. Dependabot alerts for the base image's Python packages are version-based matches against upstream advisory ranges; RHEL backports fixes without changing the version string, so verify each alert against Red Hat's advisory status for the installed RPM release before triaging — see [CONTRIBUTING](CONTRIBUTING.md#known-alert-noise-base-image-python-packages).

Updates are automated: a weekly version-aware dispatcher ([`scheduled_dispatch.yml`](.github/workflows/scheduled_dispatch.yml)) builds newer Go versions as they are released, rebuilds are dispatched automatically when an UBI base image drifts ([`ubi-drift-check.yml`](.github/workflows/ubi-drift-check.yml)), and one-off builds can be dispatched manually (`workflow_dispatch` with a `go_version` input). The version tracks above are generated from live go.dev and Quay data by [`readme-tracks.yml`](.github/workflows/readme-tracks.yml).

<details>
<summary><strong>FIPS variants — backends, tags, and runtime differences</strong></summary>

FIPS variants track [golang-fips/go](https://github.com/golang-fips/go) releases per supported Go minor, preferring stable releases and falling back to prereleases when a minor has no stable release yet.

Tag names state the FIPS backend the image actually uses: `openssl-fips`
for the Go ≤1.26 toolchains (cryptography routed through the OpenSSL FIPS
module) and `hostfips` for Go 1.27+ (native `crypto/fips140`) — e.g.
`ubi9-openssl-fips-v1.26.10` and `ubi9-hostfips-v1.27.3-pre`. Each prefix's
`latest[-pre]` aliases track the newest content of their own generation.

The upstream FIPS approach changed with Go 1.27; the builder builds whatever golang-fips ships per minor:

| Go | golang-fips tag | FIPS implementation |
| --- | --- | --- |
| up to 1.26 | `*-openssl-fips` | Cryptography routed through the OpenSSL FIPS module — deprecated upstream, historical sources live on the `go1.*-fips-release` branches ([migration notes](https://github.com/golang-fips/go#migration-to-upstream-fips-certified-cryptography)) |
| 1.27 and newer | `*-hostfips-release` | Go's native, CMVP-certified `crypto/fips140` module with host-auto FIPS activation ([downstream modifications](https://github.com/golang-fips/go#downstream-modifications)) |

Notable differences for the 1.27+ `hostfips-release` toolchains:

- **Host-auto FIPS** — `GODEBUG=fips140=auto` is compiled in by default, so FIPS mode activates only when the host is booted in FIPS mode. Set [`GODEBUG=fips140=on`](https://github.com/golang-fips/go#godebugfips140) to force FIPS mode regardless of the host (upstream guidance: test with `fips140=only`, run with `on` or `auto`).
- **Certified module by default** — builds embed the certified FIPS 140-3 snapshot ([`GOFIPS140=certified`](https://github.com/golang-fips/go#fips-module-embedding-gofips140)); ML-DSA is unavailable in certified builds until the v1.26.0 module is certified.
- **Non-approved crypto** is recorded via the FIPS service indicator rather than producing runtime errors or panics, unlike the old OpenSSL backend.

The images keep `GOEXPERIMENT=strictfipsruntime`, which the 1.27+ toolchains still honor ([strict FIPS runtime protection](https://github.com/golang-fips/go#strict-fips-runtime-protection): abort at startup when the host is in FIPS mode but `GODEBUG=fips140` is disabled).

</details>
